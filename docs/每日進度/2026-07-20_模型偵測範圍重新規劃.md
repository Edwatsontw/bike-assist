# 2026-07-20 模型偵測範圍重新規劃（重大架構決策）

## 一、觸發原因
確認尾燈只需要「煞車／減速警示」（已由 [[AccelAnalyzer]] 完成，不需 ML）後，
重新定義視覺模型的用途：**不是即時預警，而是行車後蒐集車後路面坑洞與流浪狗的
影像紀錄，上傳伺服器備查**。此需求改變了整個部署架構的核心前提。

## 二、新需求（使用者 2026-07-20 定義）
- 偵測目標：**車後路面坑洞（pothole）＋ 流浪狗（stray dog）**
- 鏡頭方向：**車後**
- 偵測到 → **標記該張照片**
- **App／韌體端把照片回傳伺服器**
- **不需要在車上觸發任何反應**（不亮燈、不響鈴、不即時處理）

## 三、關鍵決策

### 決策 1：偵測改在「伺服器端」跑（不在 ESP32-S3 上）
既然不需要車上即時反應，模型不必跑在 MCU 上。ESP32 只負責**拍照＋上傳**，
偵測交給伺服器。

**連帶結論——espdet_pico / ESP-DL / ESP-IDF 這整條線正式擱置**：
- 之前放棄 YOLO11n、改用 espdet_pico，唯一理由是「ESP32-S3 硬體跑不動大模型」。
  偵測移到伺服器後，這個限制消失。
- 伺服器（本機 RTX 5070 或任何有 GPU/CPU 的機器）**沒有硬體限制，可直接用
  更準的 YOLO11n**（已訓練好兩輪，見下）。
- espdet_pico 的訓練/量化成果（`safeway_pico_224.espdl`）保留存檔，不再投入
  ESP-IDF 環境、框架整合、實機延遲量測等後續資源。

### 決策 2：模型類別改為 pothole + 流浪狗（移除 vehicle / safari animal）
| 類別 | 資料現況 |
|---|---|
| pothole（坑洞） | ✅ 現有 `ml/datasets/` 可直接沿用（原 class 0，6621 框） |
| 流浪狗（stray dog） | ❌ **全新類別，需重新蒐集**。現有 `animal` 類別是大象/犀牛/花豹/老虎（safari 動物），**不是狗**，無法沿用 |
| vehicle（車輛） | ⛔ 新需求不需要，移除 |

### 決策 3：流浪狗資料用「現成公開資料集」
沿用與 pothole/vehicle 相同的取得方式（Roboflow 公開資料集），成本最低。
候選資料集（YOLO 格式，可直接匯出）：
- Stray Animal Detection（859 張狗/貓，含預訓練模型）
  https://universe.roboflow.com/rep-rxi6f/stray-animal-detection
- Dog Detection（499 張，多格式含 YOLO）
  https://universe.roboflow.com/oidv4-to-yolov8/dog-detection-ul9rb
- Dogs（396 張）https://universe.roboflow.com/yolo-lggkk/dogs-4i7ne
- yolo-dog（408 張）https://universe.roboflow.com/yolov5take2/yolo-dog-yvgkj

註：這些多為一般狗（寵物/街景），非專門「台灣流浪狗」。若車後實拍角度落差大，
之後可比照 pothole 補強策略，加拍一些車後視角實照微調。新 `data.yaml` 類別擬為
`0: pothole`、`1: dog`（2 類）。

## 四、伺服器端現況（已有基礎，不用從零做）
`server/`（FastAPI）已具備：
- `POST /api/frame`：接收 ESP32 上傳的 JPEG 影格（raw bytes, image/jpeg）
- `GET /api/frame`、`/camera`：最新影格與瀏覽器即時預覽
- `POST/GET /api/data`：感測器資料（roll/pitch/加速度/GPS，見 `models.py`）

**尚缺（待做）**：
1. 在收到影格時跑 YOLO11n 偵測 pothole/dog
2. 有偵測到 → 標記該影格（存檔＋寫入偵測結果 metadata：類別、框、信心、時間、
   GPS 位置——GPS 已在 `/api/data` payload 內，可關聯）
3. 儲存/瀏覽被標記的影像（可延伸現有 `/camera` 頁或加一個 gallery）

## 五、整體運作構想（2026-07-20 使用者定義，站點批次上傳架構）

不是騎乘中即時上傳，而是 **store-and-forward（歸還站批次回傳）**：

```
騎乘中                          歸還時                        伺服器
┌─────────────────┐   ┌──────────────────┐   ┌─────────────────────────┐
│ 拍照 → 存 SD 卡  │ → │ 連上歸還站點服務機 │ → │ YOLO11n 辨識 pothole/dog │
│ （附 GPS＋時間） │   │ 的 WiFi，回傳整趟  │   │ → 標記照片               │
│ 不做任何即時處理  │   │ 所有數據（照片＋   │   │ → 對應 GPS 座標打上地圖  │
│                 │   │ log＋感測資料）    │   │ → 分類儲存               │
└─────────────────┘   └──────────────────┘   └─────────────────────────┘
```

- 腳踏車歸還站點設有**服務機**（站點主機），車上 ESP32 歸還時連上它的 WiFi
- 上傳完成後伺服器端進行辨識與標記（含大量資料的持續訓練迭代）
- 每張被標記的照片依其 **GPS 座標標上地圖並分類**（坑洞地圖／流浪狗出沒點）
- 好處：車上不需行動網路（無 SIM）、騎乘中不耗上傳電力、WiFi 只在站點用

### 韌體端待做
- **（關鍵缺口，最優先）`/dashcam/log.csv` 目前只記
  `index,event,roll,pitch,accel,filename`，沒有 GPS 座標與時間戳**——
  「照片對應地圖座標」整個構想的前提。需在 `recordFrame()` 寫 log 時加上
  `lat,lon,timestamp`（GPS 已有 [[GPSModule]]，時間已有 NTP/GPS 校時，資料都在，
  只是沒寫進去）
- 現況：`NetworkManager` 模組存在但**被排除在編譯外**，目前拍照只存 SD 不上傳
- 待做：歸還站上傳模式——偵測到站點 WiFi（特定 SSID）→ 把 SD 卡整趟資料
  （影像＋log.csv）批次 POST 到伺服器 → 成功後清理 SD 空間
- 相機方向確認為**車後**（實體安裝方向需確認/調整）
- 擷取解析度：240×240 與伺服器端 YOLO11n（224/320 訓練）相容；由於已無
  on-device 推論顧慮，可考慮調回較大尺寸讓伺服器抓小目標坑洞更準，
  代價只剩 SD 空間與站點上傳時間

### 伺服器端待做
- 批次接收端點（現有 `/api/frame` 是單張即時用，需加一個批次上傳 API，
  含影像檔＋log.csv metadata 關聯）
- YOLO11n 推論 pothole/dog → 有偵測到的照片標記存檔（類別、框、信心）
- 依 log.csv 的 GPS 座標把標記結果放上**地圖**（坑洞地圖／流浪狗分布），分類瀏覽
- 資料持續累積後的再訓練流程（收集到的真實車後影像回流進訓練集）

## 六、待辦（新路線，優先序）
1. 韌體：log.csv 補 GPS 座標＋時間戳（地圖標記的前提，改動小）
2. 下載/合併流浪狗公開資料集，與現有 pothole 重組成 2 類 `data.yaml`
3. 用 YOLO11n 重新訓練 pothole + dog（沿用 `.venv-train` 環境，本機 RTX 5070）
4. 伺服器：批次上傳 API + YOLO11n 推論標記 + GPS 地圖分類
5. 韌體：站點 WiFi 批次上傳模式（`NetworkManager` 重新啟用改造）
6. 端到端測試：騎乘拍照 → 歸還連 WiFi 上傳 → 伺服器標記 → 地圖呈現
